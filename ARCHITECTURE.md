# HomeTutor — Architecture

## What this is

A tutor-marketplace web app (same category as Urban Company / UrbanClap, but
for finding home tutors). Three user roles — **Student**, **Tutor**, **Admin**
— share one backend and one frontend codebase.

## High-level shape

```
┌─────────────────────────┐        HTTPS / JSON        ┌──────────────────────────────┐
│   Frontend (FrontEnd/)  │  ───────────────────────►  │   Backend (BackEnd/)          │
│   Next.js 13 App Router │  ◄───────────────────────  │   ASP.NET Core 10 Web API     │
│   TypeScript + Tailwind │        JWT bearer token      │   C#, REST, Controllers       │
└─────────────────────────┘                             └───────────────┬──────────────┘
                                                                          │
                                                                          │ EF Core 9
                                                                          ▼
                                                          ┌──────────────────────────────┐
                                                          │   PostgreSQL                  │
                                                          └──────────────────────────────┘

External services: Razorpay (payments), Cloudinary (image upload), SMTP via MailKit (password reset).
```

Two independent projects, no shared code. They only communicate over HTTP.
The frontend has **no server-side logic of its own** — every piece of real
data comes from the backend API; the frontend is purely presentation +
client-side state.

## Backend (`BackEnd/HomeTutorAPI/`)

**Stack**: ASP.NET Core 10 (Web API, controller-based, not minimal APIs) · EF
Core 9 · PostgreSQL (via Npgsql) · AutoMapper · JWT bearer auth · BCrypt
password hashing · Razorpay SDK · Cloudinary SDK · MailKit.

**Layout**:
```
Controllers/     — one controller per resource area (thin, HTTP-facing)
DTOs/            — all request/response shapes, single file (DTOs.cs)
Models/          — EF Core entity classes + enums, single file (Models.cs)
Data/            — AppDbContext: fluent config + seed data (HasData)
Helpers/         — AutoMapper profile (entity ↔ DTO mapping)
Repositories/    — thin repository interfaces/implementations per aggregate
Services/        — cross-cutting services (JWT issuing, etc.)
Extensions/      — DI/startup wiring helpers
Migrations/      — EF Core migrations (see below — one is hand-authored)
Program.cs       — composition root: DI, middleware pipeline, CORS, auth
```

**Controllers** (all under `/api/{controller}`):
- `AuthController` — register (student/tutor), login, refresh, password reset
- `StudentsController` — student profile, requirements, enquiries sent, wallet
  (`[Authorize(Roles="Student")]`)
- `TutorsController` — public search/detail, tutor's own profile, stats,
  wallet, enquiries received, availability
- `PaymentsController` — subscription plans, coin packages, Razorpay
  order creation + verification
- `AdminController` — dashboard stats, tutor approval, user management,
  payment/requirement listings (`[Authorize(Roles="Admin")]`)
- `LookupsController` — subjects, cities, teaching levels (public reference data)

**Auth model**: JWT bearer tokens with refresh tokens. `[Authorize(Roles=...)]`
gates most endpoints. The caller's role is always re-derived server-side from
the authenticated user (never trusted from the request body) — this matters
for the subscription-plan authorization described below.

**Data model** (`Models/Models.cs`) — key entities:
- `User` (role: Student/Tutor/Admin) → 1:1 → `StudentProfile` / `TutorProfile`
- `TutorProfile` ↔ `Subject` via `TutorSubject` (many-to-many)
- `TuitionRequirement` — a student's posted "I need a tutor for X" request
- `Enquiry` — a student's direct contact-a-tutor action
- `Review` — student review of a tutor
- `SubscriptionPlan` → `TutorSubscription` / `StudentSubscription` (role-scoped
  purchases against a shared plan catalog)
- `Payment`, `CoinTransaction` — Razorpay payment records and the coin ledger
- `Availability` — a tutor's weekly time slots

**Subscription plans & audience** (added in this integration pass): plans
live in one `SubscriptionPlans` table, each tagged with a `PlanAudience`
(`Student` / `Tutor` / `Both`). `GET /api/payments/plans?audience=Student|Tutor`
filters server-side. `POST /api/payments/create-order` independently
re-validates that the caller's actual role matches the plan's audience
before creating a Razorpay order — this is enforced in the controller, not
just hidden in the frontend, so the API itself refuses a mismatched purchase.

**Migrations**: `Migrations/` contains two "real" (tool-generated) migrations
and one hand-authored one:
- `20240101000000_InitialCreate.cs` / `20260709121031_InitialCreate.*` —
  original schema, generated by `dotnet ef migrations add`.
- `20260817000000_AddSubscriptionPlanAudience.cs` — **hand-authored**, added
  during this integration work because no .NET SDK / NuGet access was
  available in that session to run the EF tooling. It has no companion
  `Designer.cs`. Before adding any further migrations, run
  `dotnet ef migrations add <name>` locally once so EF regenerates a proper
  model snapshot from the real, tooling-verified state.

## Frontend (`FrontEnd/`)

**Stack**: Next.js 13 (App Router) · TypeScript · Tailwind CSS · shadcn/ui
(Radix primitives) · axios · Razorpay checkout.js (loaded via `<Script>` in
the root layout).

**Layout**:
```
app/                     — route segments (App Router)
  (main)/page.tsx         — public home page
  search/                 — tutor search & filtering
  tutor/[id]/             — tutor detail/profile
  register/student|tutor/ — signup forms
  post-requirement/       — student posts a tuition requirement
  wallet/                 — coin balance, purchase, transaction history
  pricing/                — public plan comparison (student + tutor sections)
  subscription/           — logged-in checkout flow (student plans)
  dashboard/student|tutor|admin/ — role-specific dashboards
components/              — shadcn/ui primitives + shared components (header, footer, tutor-card)
lib/
  api.ts                  — the ONLY place that talks to the backend (see below)
  types.ts                — shared frontend-facing types (Tutor, Student, Transaction, ...)
  utils.ts                — small helpers (cn(), etc.)
```

**`lib/api.ts` is the integration boundary.** Every page imports from here,
never calls `fetch`/`axios` directly, and never imports mock data. It's
organized as one export per backend resource area (`authApi`, `tutorsApi`,
`studentsApi`, `paymentsApi`, `adminApi`, `lookupsApi`), plus:
- An axios instance with request/response interceptors that attach the JWT
  and silently refresh it on 401.
- An **adapter layer** that translates backend DTO shapes into frontend-
  friendly shapes where they genuinely differ (see "Known shape mismatches"
  below) — the backend's contract is not always identical to what the UI
  types expect, and this file is where that gap is closed.
- `openRazorpay()` — wraps the Razorpay checkout modal and calls
  `paymentsApi.verifyPayment` in its success handler.

**Auth**: JWT + refresh token stored in `localStorage` (`accessToken`,
`refreshToken`, `user`). `authApi.isLoggedIn()` / `authApi.getUser()` are the
two functions pages use to check auth state — there's no global auth
context/provider; each page checks independently.

## Known shape mismatches between backend and frontend (handled in `lib/api.ts`)

These aren't bugs left in place — they're deliberate translations, documented
here so they aren't "fixed" twice or fixed in the wrong layer:

| Backend sends | Frontend expects | Where reconciled |
|---|---|---|
| `isVerified: bool` | `verified: bool` | `mapTutor()` |
| `mode: "Online"\|"Offline"\|"Both"` (string) | `mode: ('online'\|'offline'\|'both')[]` (array) | `mapMode()` |
| `balance`, `createdAt`, `balanceAfter`, `Credit`/`Debit` (capitalized) | `coinBalance`, `date`, `balance`, lowercase `credit`/`debit` | `mapWallet()` |
| `EnquiryDto` has both `TutorName`+`StudentName`, only one populated depending on which controller queried it | UI picks whichever is present per context | `Enquiry` type, consumed directly in dashboards |

If the backend's DTO shapes change, update the corresponding `map*()`
function in `lib/api.ts` rather than reshaping data inside individual pages.

## Known gaps (real, not implemented — don't build UI assuming they exist)

- **No class/session scheduling.** No booking table, no timetable endpoint.
  Dashboards say so explicitly instead of showing fabricated sessions.
- **No tutor-side messaging/chat.** Only one-shot `Enquiry` records exist
  (a student contacts a tutor once); there's no conversation thread.
- **No yearly billing.** `SubscriptionPlan.DurationDays` is fixed per plan
  (currently always 30 for paid plans); there is no annual price field.

## External integrations

- **Razorpay** — `PaymentsController.CreateOrder` creates a Razorpay order
  server-side; the frontend opens Razorpay's checkout modal
  (`openRazorpay()` in `lib/api.ts`) and calls `verify` on success, which is
  where the signature is checked and the subscription/coin balance actually
  gets applied.
- **Cloudinary** — tutor profile image upload (`TutorsController`).
- **MailKit (SMTP)** — password reset emails (`AuthController`).

## Environment / config


- Backend: `appsettings.json` / `appsettings.Development.json` — Postgres
  connection string, JWT signing key, Razorpay keys, Cloudinary/SMTP config.
- Frontend: `.env.local` — `NEXT_PUBLIC_API_URL` (points at the backend's
  `/api` root, e.g. `http://localhost:5000/api`).
